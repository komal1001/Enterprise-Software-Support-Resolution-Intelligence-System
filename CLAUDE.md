NIIT Capstone Project — LinkedIn Portfolio Build

## Project Goal
Production-grade autonomous agentic AI system that triages enterprise SaaS support tickets:
classifies intent, routes to the right retrieval pipeline, re-evaluates severity, escalates
critical/low-confidence cases, and returns cited responses.

Target roles: AI Solutions Engineer, Support Engineering, LLM Application Engineer.

## The 4 Routing Paths

```
RAG         → Agent1 → Agent2 → Agent4 → Response
SQL         → Agent1 → Agent3 → Agent4 → Response
Hybrid      → Agent1 → Agent3 → Agent2(SQL-enriched query) → Agent4 → Response
Multi-Agent → Agent1 → Agent3 → Agent2(SQL-enriched query) → Agent4 → Agent5 → Response

Note: Agent numbering reflects function role, not execution order.
For Hybrid/Multi-Agent, Agent 3 (SQL) runs before Agent 2 (RAG) so that
customer tier, region, and incident context from SQL can enrich the RAG query.
RAG-only tickets still run Agent 2 first (no SQL needed).
```

Routing is determined by Agent 1's `routing_path` output.
Multi-Agent path always triggers escalation (severity High or Critical).

## Key Architecture Decisions (ADRs)

| ADR | Decision | Why |
|---|---|---|
| ADR-001 | LangGraph over CrewAI | Deterministic routing enforces SLOs #10, #11, #5. CrewAI autonomy cannot guarantee 100% escalation recall. |
| ADR-002 | LLM-to-SQL with sqlglot guardrails, not parameterized templates | Scales to unlimited query types without a template per intent. Safety enforced at query layer: sqlglot AST rejects any non-SELECT statement; ALLOWED_TABLES allowlist blocks unauthorized tables; MAX_ROWS=100 caps result size. SLO #3 (SQL Correctness ≥ 95%) is a statistical target backed by eval, not a hard guarantee — acceptable trade-off for scalability. |
| ADR-003 | pgvector in PostgreSQL for embeddings | Single DB for structured + vector data, simplifies ops |
| ADR-005 | Agent 4 runs on every ticket | Safety net — even RAG-only tickets can contain hidden Critical signals |
| ADR-006 | LLM-as-judge for golden set evaluation | GPT-4o mini scores responses against answer_rubric |
| ADR-007 | TSR ≥ 90% binary pass/fail | Industry standard from Zendesk AI Benchmark 2024 |
| ADR-008 | Multi-topic tickets: classify primary signal only | Priority ladder picks highest-risk category; secondary captured in reasoning |
| ADR-009 | React frontend calls FastAPI via fetch/axios | Decoupled frontend/backend; SSE streaming for real-time responses |
| ADR-010 | LlamaParse + MarkdownNodeParser + SentenceSplitter fallback, no metadata filtering, rank_bm25 for BM25 (pure Python, no C++ build tools) | **LlamaParse** (not pypdf/Unstructured): multimodal parser converts PDF visual structure to markdown `##` headers; extracts tables as markdown; describes images inline. **MarkdownNodeParser** (not SentenceSplitter alone): splits at `##` headers keeping tables intact — SentenceSplitter splits mid-table making structured data useless. **SentenceSplitter fallback**: sections can be arbitrarily long — splits any node over 2000 chars. **No metadata filtering**: 7 documents are interconnected — TC-50 needs both ITIL (incident response) and SLA doc (1-hour notification rule) for one ticket; ExactMatchFilter on production_incident would silently miss the SLA doc. OR filters require hardcoding category combinations — same maintenance problem as explicit mapping. Semantic similarity across all 7 documents is more correct and requires zero maintenance. |
| ADR-011 | `with_structured_output` over `PydanticOutputParser` for LLM responses | `PydanticOutputParser` relies on text instructions — LLM can add preamble ("Sure! Here is...") or return wrong casing (`"sql"` vs `"SQL"`) breaking routing. At temperature=0, failure is deterministic for specific ticket patterns — not random. `with_structured_output` sends Pydantic schema as an OpenAI function/tool definition; API enforces schema before response reaches our code. Required for SLO #10 (Critical Misclassification Rate < 3%). `include_raw=True` preserves token counts for Langfuse (SLO #14). Retry: 3 attempts, exponential backoff (1s, 2s). Fallback: ambiguous/Multi-Agent/confidence=0.0 → Agent 5 escalates, user sees plain-language message. |
| ADR-012 | Neon (serverless PostgreSQL) over Supabase for cloud database | Both support pgvector and standard PostgreSQL connections. Supabase free tier **pauses the database after 7 days of inactivity** — the next request takes 20–30s to wake it, which is unacceptable during a live portfolio demo. Neon free tier **never pauses projects**; it only suspends compute after 5 minutes of inactivity (cold start ~1–2s on the next query, not 30s). For a portfolio project with irregular traffic, a 2s cold start is forgettable; a 30s hang while an interviewer watches is not. Both have 512 MB free storage — sufficient for 120 customers, 1000 tickets, 50 incidents, and 155 pgvector nodes. Migration path: `pg_dump` local → restore to Neon → update `DATABASE_URL` in `.env`. |
| ADR-013 | ThreadPoolExecutor (max_workers=4) for parallel eval execution | Sequential eval of 18 TC cases takes ~10 min (each case: Agent 1→4→synthesizer + LLM judge = ~35s). ThreadPoolExecutor cuts this to ~3 min. max_workers=4 keeps Azure OpenAI within rate limits (10 RPM on free tier) while still achieving 3-4x speedup. `_print_lock` (threading.Lock) serialises progress output. Results sorted by tc_id after `as_completed` since thread completion order is non-deterministic. Each case gets its own UUID thread_id so MemorySaver state never leaks between parallel cases. Requires `nest_asyncio.apply()` at eval.py module level — LlamaIndex's PGVectorStore uses asyncpg internally; without this patch, worker threads raise "Detected nested async" errors when multiple threads try to run async retrieval concurrently. |
| ADR-014 | Per-thread `QueryFusionRetriever` + global nodes cache in rag.py | Original `retrieve()` rebuilt the pgvector connection, loaded nodes_cache.json, and rebuilt BM25 on every ticket call (~200ms wasted). Fix uses two levels: (1) `_nodes` global singleton — nodes JSON loaded once, read-only after init, safe to share across threads; (2) `threading.local()` (`_thread_local.retriever`) — one `QueryFusionRetriever` per OS thread. asyncpg connections are NOT thread-safe; a single shared retriever causes `InterfaceError` under the parallel eval `ThreadPoolExecutor`. Per-thread singletons give FastAPI (effectively single-threaded per worker) a warm connection on every request, while letting the eval's 4-thread pool use 4 independent connections without contention. |
| ADR-015 | `psycopg2.ThreadedConnectionPool` for SQL agent + centralised Langfuse prompt cache | **Problem**: `_execute()` called `psycopg2.connect()` on every ticket — opening a new TCP connection each time. On Neon (serverless), this also risks waking the compute from a 5-minute idle suspension, adding 1-2s per ticket. **Connection pool fix**: `ThreadedConnectionPool(minconn=1, maxconn=5)` opened once at module level; `_execute()` calls `_get_conn()` (borrows a live connection) and `pool.putconn()` (returns it). Auto-reconnect: before returning a connection, `_get_conn()` pings with `SELECT 1` — if the connection went stale (Neon killed it), it discards it and gets a fresh one. **Prompt cache fix**: `lf.get_prompt()` makes an HTTP round-trip to Langfuse cloud on every agent call (~200-400ms). Centralised `get_cached_prompt(name)` in `langfuse_client.py` — double-checked lock, fetches each prompt once per process lifetime, all 6 agents share the same cache dict. Saves up to ~1.8s per ticket (6 agents × ~300ms). Trade-off: cached prompt won't reflect Langfuse dashboard edits until process restart — acceptable for a pinned production prompt. |
| ADR-017 | In-memory semantic cache + embedding model singleton for RAG-only retrieval | **Problem 1 — Repeated retrieval cost**: Every RAG ticket embeds the query + runs pgvector similarity search + BM25 scoring (~500ms total). Documentation answers are not customer-specific — "How do I configure OAuth?" and "How do I set up OAuth authentication?" should return the same chunks. **Semantic cache fix**: `semantic_cache.py` stores `(query_vector, chunks)` pairs in an `OrderedDict` (LRU eviction at 200 entries). On each RAG query: embed → scan cache for cosine similarity >= 0.92 → hit returns cached chunks instantly (~0ms), miss runs normal retrieval and stores result. Safe only on RAG route — Hybrid/Multi-Agent queries enriched with SQL customer context bypass the cache (`use_cache=False` in `agent2_rag.py`). **Problem 2 — Double embedding on cache miss**: Original design called `embed_model.get_text_embedding(query)` inside `cache_lookup()` (1 API call), then LlamaIndex's retriever embedded the same query again internally (2nd API call) — doubling the embedding cost on every miss. **Fix**: `retrieve()` embeds the query ONCE using `_get_embed_model()`, passes the pre-computed vector to `cache_lookup(vector)` and `cache_store(vector, chunks)`. LlamaIndex still re-embeds internally for pgvector (unavoidable — can't inject a pre-computed vector into QueryFusionRetriever), but the cache check no longer adds an extra API call. **Problem 3 — Embedding model rebuilt on every call**: `_build_embed_model()` was called on each `retrieve()` invocation, constructing a new `AzureOpenAIEmbedding` object (reads env vars, initialises HTTP client) each time. **Singleton fix**: `_embed_model_singleton` global in `rag.py` — built once on first call, reused across all threads (object is stateless and thread-safe). Saves ~10-20ms model init overhead per ticket. **Threshold 0.92**: matches genuinely equivalent phrasings while rejecting loosely related questions. **Stats**: `cache_stats()` logged to Langfuse metadata on every RAG span. `cache_clear()` called between eval runs to avoid cross-contamination. |
| ADR-018 | pgvector index deferred — HNSW at production scale (10k+ vectors), not at 155 nodes | **What a vector index does**: By default pgvector performs an exact full scan — every query vector is compared against every stored vector sequentially. An index organises vectors into a structure so only a small subset needs to be checked. Two options: **IVFFlat** groups vectors into clusters, searches the nearest cluster only (approximate, fast, less memory). **HNSW** (Hierarchical Navigable Small World) builds a graph of vector connections, hops through the graph to nearest neighbours (more accurate than IVFFlat, faster queries, more memory). HNSW is the recommended index type for pgvector in production. **Why deferred**: Our corpus is 155 nodes (7 PDFs). A full sequential scan over 155 vectors takes ~1-2ms — negligible. Index build overhead (~5-10ms per query for graph traversal setup) and memory cost outweigh any benefit at this scale. **Production scaling path**: When the knowledge base grows beyond ~10,000 vectors (e.g. adding more product docs, historical ticket resolutions, KB articles), add HNSW index: `CREATE INDEX ON data_document_chunks USING hnsw (embedding vector_cosine_ops) WITH (m=16, ef_construction=64);` — `m=16` controls graph connectivity (higher = more accurate, more memory), `ef_construction=64` controls build quality. Query then uses `SET hnsw.ef_search=40` to control recall vs speed trade-off. Expected speedup at 100k vectors: full scan ~100ms → HNSW ~2-5ms. |
| ADR-016 | LLM computation caching — Azure prefix cache + `prompt_cache_key` + no InMemoryCache | **LLM caching** reuses prior LLM computation instead of recomputing for identical prompt contexts. Three layers considered: (1) **Azure OpenAI automatic prefix caching + `prompt_cache_key`** — Azure caches the KV computation for any prompt prefix > 1024 tokens. Our agent system prompts are all > 1024 tokens, so the fixed parts (schema, guardrail rules, tone instructions) are cached at the API level. `prompt_cache_key: "langchain-prompt-caching"` added to `model_kwargs` on all 6 LLM instances — this groups requests from the same deployment together so Azure routes them to the same server cache, improving hit rate in distributed/load-balanced deployments. Without it, requests can go to different servers each with their own cache, making hits inconsistent. (2) **LangChain `InMemoryCache`** — caches complete LLM responses for *identical* inputs. Decided against: every support ticket is a unique question, so exact-match hit rate is ~0%. (3) **Semantic cache for LLM responses** — decided against for SQL/Hybrid routes: similar ticket text can require completely different customer-specific answers. Safe for RAG-only documentation answers → implemented at retrieval level (ADR-017) where we cache chunks, not the LLM response. **Conclusion**: Azure prefix cache + `prompt_cache_key` covers LLM-level caching. Retrieval-level semantic cache covers RAG. InMemoryCache rejected. |

## Latency Optimisation Decisions (SLO #5/#6)

| Layer | Problem | Fix | ADR |
|---|---|---|---|
| SQL DB connection | `psycopg2.connect()` on every ticket → new TCP + Neon cold start (~1-2s) | `ThreadedConnectionPool(minconn=1, maxconn=5)` — reuse open connections; auto-ping to detect stale connections | ADR-015 |
| Langfuse prompt fetch | `lf.get_prompt()` HTTP call on every agent call × 6 agents (~300ms each = ~1.8s/ticket) | `get_cached_prompt()` in `langfuse_client.py` — fetch once per process, shared across all agents | ADR-015 |
| RAG retriever rebuild | `QueryFusionRetriever` + BM25 rebuilt on every ticket (~200ms) | Per-thread singleton in `_thread_local`; global `_nodes` loaded once from JSON | ADR-014 |
| LLM prefix computation | Repeated static system prompt sent to Azure on every call | Azure OpenAI automatic prefix caching (free, active for prompts > 1024 tokens) — no code needed | ADR-016 |
| LangChain InMemoryCache | Would cache complete LLM responses for identical inputs | **Rejected** — hit rate ~0% on unique support tickets; semantic cache also rejected (safety risk: could return cached answer for wrong customer) | ADR-016 |
| Neon cold start on startup | First ticket after server start hits unwarmed Neon compute (~10-30s) | Startup warmup ping in `main.py` `@app.on_event("startup")` — wakes Neon before first ticket arrives | ADR-012 |
| RAG embedding + pgvector search | Embedding API call + pgvector ANN search + BM25 on every RAG ticket (~500ms) | `semantic_cache.py` — cosine similarity >= 0.92 against cached query vectors returns chunks instantly. RAG-only route only; Hybrid/Multi-Agent bypass cache (customer-specific context). pgvector index deferred — see ADR-018. | ADR-017, ADR-018 |
| RAG + SQL sequential on Hybrid | SQL runs, then RAG uses SQL output to enrich query — inherently sequential | Cannot parallelise: RAG query enrichment requires SQL customer/tier context first. Accepted trade-off. | ADR (design) |

  stronger model for low-volume but high-stakes Agent 4 re-assessment.
  Trade-off: GPT-4o full is ~15x more expensive per token — only justified for Agent 4, not Agent 1.

## Sprint 7 Notes
Rate limiting is the third NL2SQL safety principle (NIIT slide: Intent Gating / Constrained Exposure / Rate Limiting).
Two layers needed:

- **API-level rate limiting** (`src/api/main.py`):
  Add `slowapi` middleware — `@limiter.limit("10/minute")` on POST /ticket keyed by IP address.
  Also consider per-thread_id limiting to block a single user from spamming 100 tickets (cost spike, SLO #14).
  Package: `slowapi>=0.1.9` — add to requirements.txt.

- **DB query timeout** (`src/retrieval/sql.py` → `_execute()`):
  Add `SET statement_timeout = '5s'` before executing the generated SQL.
  Kills runaway queries before they degrade DB performance. Complements MAX_ROWS=100 which
  only caps result size, not execution time.
